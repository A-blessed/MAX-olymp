# Развёртывание на my-olymp.ru

Постоянный домен заменяет туннель. Всё решение живёт на одном адресе:

| Адрес                        | Что отдаёт                                  |
|------------------------------|---------------------------------------------|
| `https://my-olymp.ru/`       | мини-приложение, статика из `frontend/`      |
| `https://my-olymp.ru/api/*`  | API, авторизация по подписи данных запуска    |
| `https://my-olymp.ru/webhook`| события бота от платформы MAX                 |
| `https://my-olymp.ru/health` | проверка живости                              |

Один origin на фронтенд и API — это не только удобство: браузер не делает
preflight, CORS в бою не участвует вовсе, а заголовок-костыль
`ngrok-skip-browser-warning` больше не нужен и удалён.

---

## Что должно быть на сервере

* Linux — Ubuntu 22.04/24.04, Debian 12 или любой другой, где ставится
  Docker. Хватает 1 ГБ памяти и 10 ГБ диска;
* Docker с Compose v2 и git. На чистой Ubuntu или Debian — две команды:

  ```bash
  curl -fsSL https://get.docker.com | sudo sh
  sudo apt-get install -y git
  ```

  Проверить: `docker compose version` отвечает `v2.…` или новее;
* открытые извне порты **80** и **443** (80 нужен не только для
  редиректа — через него Let's Encrypt подтверждает владение доменом);
* A-запись `my-olymp.ru` на IP этого сервера — см. шаг 0. Если заводите ещё
  и `www`, A-запись для него тоже должна существовать **до** выпуска
  сертификата.

---

## 0. Домен: что делает его владелец

Домен и сервер могут быть у разных людей — у нас так и есть. Тогда
владельцу домена нужно сделать ровно одно: **направить домен на IP
сервера**. Больше от него ничего не требуется.

Сначала — чего делать **не** надо:

* **Покупать SSL-сертификат у регистратора.** HTTPS выписывает certbot
  бесплатно, автоматически и сам продлевает. Купленный сертификат придётся
  ставить руками и обновлять руками каждый год.
* **Заказывать хостинг у регистратора.** Домен и сервер не связаны:
  домен — это запись в DNS, сервер — отдельная машина.

### Что настроить в панели регистратора

В разделе DNS (у регистраторов он называется «DNS-записи», «Управление
зоной», «DNS-серверы и управление зоной»):

| Тип | Имя (хост) | Значение | TTL |
|---|---|---|---|
| `A` | `@` или пусто — это сам `my-olymp.ru` | IP сервера | 300 |
| `A` | `www` | тот же IP | 300 |

`@` — обязательна, `www` — по желанию; если её не делать, удалите блок
`www` из [`deploy/nginx/my-olymp.ru.conf`](../deploy/nginx/my-olymp.ru.conf)
и не указывайте `-d www.my-olymp.ru` при выпуске сертификата.

TTL на время переезда лучше поставить минимальный: если IP придётся
поменять, новый разъедется за минуты, а не за сутки.

**Удалить всё остальное, что регистратор завёл сам:**

* записи парковки и «заглушки» — обычно `A` на IP регистратора;
* включённое перенаправление домена (redirect / «веб-форвардинг»): оно
  перебивает A-запись, и сервер вы так и не увидите;
* `AAAA`-записи, если они ведут не на наш сервер. Браузер предпочитает
  IPv6, а nginx у нас слушает только IPv4 — с чужой `AAAA` сайт будет
  открываться через раз;
* `CNAME` на самом домене: на `@` его быть не должно, он конфликтует с `A`.

### Самая частая ошибка

Записи правятся в панели, которая **не** обслуживает домен. Если
NS-серверы домена указывают на одного провайдера (скажем, на Cloudflare
или на старый хостинг), а зону вы правите у регистратора, изменения ни на
что не влияют.

Проверить, кто отвечает за домен:

```bash
dig +short NS my-olymp.ru
```

Что вернулось — та панель и нужна.

### Если домен ведут через Cloudflare

Оставьте режим **DNS only** (серая тучка), а не «Proxied». Проксирование
подменяет TLS на свой и добавляет ещё один слой, который придётся
отлаживать вместе с вебхуком MAX; выигрыша для нас в нём нет.

### Проверка

Домен разъезжается от нескольких минут до нескольких часов. Готово, когда
обе команды показывают IP сервера:

```bash
dig +short my-olymp.ru
dig +short www.my-olymp.ru
```

Пока `dig` пуст или показывает чужой адрес — **к шагу 2 переходить нельзя**:
Let's Encrypt не подтвердит владение доменом, а у него лимит 5 неудачных
проверок в час. Проще подождать, чем упереться в лимит.

Когда `dig` показывает нужный IP, владелец домена свободен: всё остальное
делается на сервере.

## 1. Код и настройки

```bash
git clone https://github.com/A-blessed/MAX-olymp.git
cd MAX-olymp
cp .env.example .env
```

В `.env` заполнить:

| Переменная        | Значение                                            |
|-------------------|-----------------------------------------------------|
| `BOT_TOKEN`       | токен бота                                          |
| `BOT_USERNAME`    | ник бота без `@`                                    |
| `WEBHOOK_SECRET`  | произвольная строка 5–256 символов `[A-Za-z0-9_-]`  |
| `POSTGRES_PASSWORD` | обязателен, только буквы и цифры. Без него compose не стартует. Задаётся до первого `up`: база запоминает пароль при создании |
| `CERTBOT_EMAIL`   | почта для писем об истечении сертификата            |

`PUBLIC_BASE_URL=https://my-olymp.ru` и `CORS_ORIGINS=https://my-olymp.ru`
уже стоят в шаблоне — менять их не нужно.

`APP_ENV` из `.env` в проде не читается: `docker-compose.prod.yml` жёстко
ставит `production`, иначе схема API открылась бы наружу молча.

Сертификаты Минцифры положить в `certs/` — без них бэкенд не установит
TLS-соединение с `platform-api2.max.ru`. Это отдельная история от
сертификата домена, они не взаимозаменяемы:

| Сертификат          | Зачем                                    | Откуда           |
|---------------------|------------------------------------------|------------------|
| Минцифры, `certs/`  | бэкенд → `platform-api2.max.ru`          | Госуслуги        |
| Let's Encrypt       | браузер и MAX → `my-olymp.ru`            | certbot, шаг 2   |

## 2. Сертификат домена

Курица и яйцо: nginx не поднимется без файла сертификата, а certbot не
сможет подтвердить домен через nginx, пока тот не поднялся. Поэтому
**первый** выпуск делается в режиме `--standalone`, когда порт 80 ещё
свободен, — то есть до первого `up`. `.env` к этому моменту уже должен
быть заполнен: compose читает его целиком даже ради одного certbot.

```bash
docker compose -f docker-compose.prod.yml run --rm -p 80:80 \
  --entrypoint certbot certbot \
  certonly --standalone --non-interactive --agree-tos \
  --email ВАША@ПОЧТА --no-eff-email \
  -d my-olymp.ru -d www.my-olymp.ru
```

Если A-записи для `www` нет — уберите `-d www.my-olymp.ru`, иначе выпуск
упадёт на проверке домена. В этом случае удалите и серверный блок `www`
из [`deploy/nginx/my-olymp.ru.conf`](../deploy/nginx/my-olymp.ru.conf):
без сертификата на `www` он отдаёт браузеру ошибку.

Сертификат ложится в том `letsencrypt` — не в репозиторий: закрытый ключ
не должен попасть в git даже случайно.

**Продление автоматическое.** Сервис `certbot` дважды в сутки вызывает
`renew` (до истечения срока больше 30 дней он ничего не делает), а nginx
раз в сутки перечитывает конфигурацию и подхватывает новый файл без
перезапуска и без обрыва соединений.

## 3. Запуск

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Поднимутся четыре сервиса: `db`, `backend`, `nginx`, `certbot`. Образы
`backend` и `nginx` собираются из исходников тут же, меньше чем за
минуту. Схему базы Alembic применяет сам при старте бэкенда, а пустой
каталог наполняется выгрузками из `backend/data/` — руками ничего
импортировать не нужно. Что импортировалось, видно в логе:

```bash
docker compose -f docker-compose.prod.yml logs backend | grep data/
```

Проверить снаружи:

```bash
curl https://my-olymp.ru/health
```

Ожидается `{"status":"ok","env":"production","bot_configured":true,"webhook_secret_set":true}`.
Оба флага должны быть `true` — если нет, `.env` не доехал до контейнера.

И что отдаётся само приложение:

```bash
curl -I https://my-olymp.ru/
```

## 4. Подписка на события бота

Адрес вебхука сменился с туннельного на постоянный, поэтому подписку
нужно оформить заново — старая продолжает указывать на ngrok:

```bash
docker compose -f docker-compose.prod.yml run --rm backend python -m scripts.setup_webhook
```

Проверить, что осталась только одна подписка и она на новый адрес:

```bash
docker compose -f docker-compose.prod.yml run --rm backend python -m scripts.setup_webhook --list
```

Если в списке остался туннельный адрес, удалить его:

```bash
docker compose -f docker-compose.prod.yml run --rm backend \
  python -m scripts.setup_webhook --delete --url https://СТАРЫЙ-АДРЕС/webhook
```

Это важнее, чем кажется: пока подписка висит на мёртвом адресе, MAX
считает события недоставленными, а через 8 часов неудач отписывает бота
сам.

## 5. Адрес мини-приложения в кабинете MAX

**Через код этого сделать нельзя** — в Bot API нет такого метода. Только
в кабинете партнёров: **Чат-боты** → нужный бот → **⋮** →
**Настройки** → поле URL мини-приложения:

```
https://my-olymp.ru
```

Пока там стоит адрес GitHub Pages, MAX будет открывать старую копию
приложения, и никакие изменения на сервере на это не повлияют. Если
доступа к кабинету нет — адрес нужно передать организаторам.

## Если Docker на сервере не ставится

Например, Windows Server на VPS без вложенной виртуализации: Linux-
контейнеры там не запускаются. Проще взять Linux-VPS; если нельзя —
ручной вариант с Caddy описан в [deploy-without-docker.md](deploy-without-docker.md).

## Обновление кода

```bash
cd MAX-olymp
git pull
docker compose -f docker-compose.prod.yml up -d --build
```

Пересоберутся и перезапустятся только те сервисы, у которых что-то
поменялось: `backend` — при правке кода бэкенда, `nginx` — при правке
`frontend/` (статика запечена в его образ). Миграции схемы бэкенд
применяет сам при старте. Статика отдаётся с `Cache-Control: no-cache`,
иначе встроенный браузер MAX держал бы старую версию и после деплоя.

**Данные каталога** при обновлении не трогаются: автоимпорт наполняет
только пустую базу. Если в `backend/data/` приехали новые выгрузки,
загрузите их явно — импорт обновляет записи на месте и прогресс
пользователей не теряет:

```bash
docker compose -f docker-compose.prod.yml exec backend python -m scripts.import_subjects
docker compose -f docker-compose.prod.yml exec backend python -m scripts.import_schedule
```

**Проверить после обновления**, не дожидаясь утра, кому и что уйдёт в
утренней сводке:

```bash
docker compose -f docker-compose.prod.yml exec backend python -m scripts.send_reminders --users
docker compose -f docker-compose.prod.yml exec backend python -m scripts.send_reminders --dry-run
```

При старте бэкенд сам спрашивает у MAX, оформлена ли подписка на события,
и пишет об этом строку в лог (`docker compose -f docker-compose.prod.yml
logs backend | grep Подписка`). «MAX не присылает события на …» значит,
что бот глух: не узнает о запуске, не ответит на сообщения, сводки
уходить будет некому. Лечится шагом 4.

## Если что-то не работает

### Сначала — один снимок состояния

Половина поломок деплоя видна не в той строке, на которую смотришь, а в
соседней: в дате сертификата, в чужом IP у домена, в том, что контейнер
не поднялся вовсе. Пересказывать такое по кускам — долго и ненадёжно,
поэтому состояние снимается целиком одной командой, на самой машине:

```bash
bash deploy/diagnose.sh
```

На Windows, где Docker не ставится, — та же команда в PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File deploy\diagnose.ps1
```

`-ExecutionPolicy Bypass` нужен почти всегда: на Windows Server запуск
скриптов закрыт по умолчанию, и без ключа команда молча откажет.
Политику он меняет только для этого запуска.

Скрипт ничего не меняет и не перезапускает — только читает. Он собирает
в один файл `diagnostics-<дата>.txt`: версию кода, заданные переменные
окружения, состояние сервисов и их логи, срок и домены сертификата, кто
слушает 80 и 443, куда ведёт DNS и что отвечает сайт — снаружи и в обход
DNS.

Версия для Windows проверяет вдобавок то, что бывает только там:
кодировку `.env` (UTF-16 от `Out-File` — та самая причина
`UnicodeDecodeError` на старте), службу PostgreSQL, занят ли порт 80
службой IIS и есть ли в брандмауэре разрешающие правила на 80 и 443.

Файл сделан пригодным для пересылки: `BOT_TOKEN`, `WEBHOOK_SECRET`,
`POSTGRES_PASSWORD` и `CERTBOT_EMAIL` в нём заменены на `<скрыто>` — и в
самом `.env`, и в логах, куда могли просочиться. Его можно показывать
целиком, не вычитывая.

Таблица ниже — что искать в этом файле.

| Симптом | Где смотреть |
|---|---|
| `nginx: host not found in upstream "backend"` | бэкенд не стал healthy; `docker compose -f docker-compose.prod.yml logs backend` |
| 502 на `/api/*` | бэкенд упал или ещё применяет миграции; те же логи |
| 404 на `/docs` | так и задумано: `APP_ENV=production` закрывает схему |
| Приложение открылось, но данные не грузятся | адрес в кабинете MAX ведёт не на `my-olymp.ru` — например, на старую копию на GitHub Pages: она ходит в API с чужого origin, и без него в `CORS_ORIGINS` запросы отклоняются; шаг 5 |
| Бот не отвечает | подписка указывает на старый адрес или её нет вовсе; строка о подписке в логе старта, шаг 4 |
| Ошибка сертификата на `www` | сертификат выписан без `www`; либо добавьте его в certbot, либо удалите блок `www` из конфига nginx |
| `Address family not supported by protocol` в логах nginx | на хосте отключён IPv6, а в конфиге появились строки `listen [::]` |
| Certbot: `DNS problem` или `Invalid response` | домен ещё не указывает на сервер или порт 80 закрыт; шаг 0 |
| Домен открывает страницу регистратора | не снята парковка или включено перенаправление домена; шаг 0 |
| Сайт открывается через раз | лишняя `AAAA`-запись: браузер идёт по IPv6, а nginx слушает IPv4; шаг 0 |
| Бот не прислал утреннюю сводку | `docker compose -f docker-compose.prod.yml exec backend python -m scripts.send_reminders --user <id>` скажет причину: от человека не было событий бота, уведомления выключены, нет сохранённых олимпиад или сказать нечего |
| В `--users` у всех «нет событий» | MAX не присылает события серверу: нет подписки на `https://my-olymp.ru/webhook`. Шаг 4, затем каждому написать боту любое сообщение |
| «В каталоге … нет сертификатов», хотя они там | смотрите путь в самом сообщении: он абсолютный и говорит, куда приложение смотрело на самом деле |
