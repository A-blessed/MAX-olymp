# Развёртывание на my-olymp.ru

Постоянный домен заменяет туннель. Всё решение живёт на одном адресе:

| Адрес                        | Что отдаёт                                  |
|------------------------------|---------------------------------------------|
| `https://my-olymp.ru/`       | мини-приложение, статика из `frontend/`      |
| `https://my-olymp.ru/api/*`  | API, авторизация по подписи данных запуска    |
| `https://my-olymp.ru/webhook`| события бота от платформы MAX                 |
| `https://my-olymp.ru/health` | проверка живости                              |

Один origin на фронтенд и API — это не только удобство: браузер не делает
preflight, CORS в бою не участвует вовсе, а заголовок-костыль
`ngrok-skip-browser-warning` больше не нужен и удалён.

---

## Что должно быть на сервере

* Linux с установленными Docker и Docker Compose v2;
* открытые извне порты **80** и **443** (80 нужен не только для
  редиректа — через него Let's Encrypt подтверждает владение доменом);
* A-запись `my-olymp.ru` на IP этого сервера — см. шаг 0. Если заводите ещё
  и `www`, A-запись для него тоже должна существовать **до** выпуска
  сертификата.

---

## 0. Домен: что делает его владелец

Домен и сервер могут быть у разных людей — у нас так и есть. Тогда
владельцу домена нужно сделать ровно одно: **направить домен на IP
сервера**. Больше от него ничего не требуется.

Сначала — чего делать **не** надо:

* **Покупать SSL-сертификат у регистратора.** HTTPS выписывает certbot
  бесплатно, автоматически и сам продлевает. Купленный сертификат придётся
  ставить руками и обновлять руками каждый год.
* **Заказывать хостинг у регистратора.** Домен и сервер не связаны:
  домен — это запись в DNS, сервер — отдельная машина.

### Что настроить в панели регистратора

В разделе DNS (у регистраторов он называется «DNS-записи», «Управление
зоной», «DNS-серверы и управление зоной»):

| Тип | Имя (хост) | Значение | TTL |
|---|---|---|---|
| `A` | `@` или пусто — это сам `my-olymp.ru` | IP сервера | 300 |
| `A` | `www` | тот же IP | 300 |

`@` — обязательна, `www` — по желанию; если её не делать, удалите блок
`www` из [`deploy/nginx/my-olymp.ru.conf`](../deploy/nginx/my-olymp.ru.conf)
и не указывайте `-d www.my-olymp.ru` при выпуске сертификата.

TTL на время переезда лучше поставить минимальный: если IP придётся
поменять, новый разъедется за минуты, а не за сутки.

**Удалить всё остальное, что регистратор завёл сам:**

* записи парковки и «заглушки» — обычно `A` на IP регистратора;
* включённое перенаправление домена (redirect / «веб-форвардинг»): оно
  перебивает A-запись, и сервер вы так и не увидите;
* `AAAA`-записи, если они ведут не на наш сервер. Браузер предпочитает
  IPv6, а nginx у нас слушает только IPv4 — с чужой `AAAA` сайт будет
  открываться через раз;
* `CNAME` на самом домене: на `@` его быть не должно, он конфликтует с `A`.

### Самая частая ошибка

Записи правятся в панели, которая **не** обслуживает домен. Если
NS-серверы домена указывают на одного провайдера (скажем, на Cloudflare
или на старый хостинг), а зону вы правите у регистратора, изменения ни на
что не влияют.

Проверить, кто отвечает за домен:

```bash
dig +short NS my-olymp.ru
```

Что вернулось — та панель и нужна.

### Если домен ведут через Cloudflare

Оставьте режим **DNS only** (серая тучка), а не «Proxied». Проксирование
подменяет TLS на свой и добавляет ещё один слой, который придётся
отлаживать вместе с вебхуком MAX; выигрыша для нас в нём нет.

### Проверка

Домен разъезжается от нескольких минут до нескольких часов. Готово, когда
обе команды показывают IP сервера:

```bash
dig +short my-olymp.ru
dig +short www.my-olymp.ru
```

Пока `dig` пуст или показывает чужой адрес — **к шагу 2 переходить нельзя**:
Let's Encrypt не подтвердит владение доменом, а у него лимит 5 неудачных
проверок в час. Проще подождать, чем упереться в лимит.

Когда `dig` показывает нужный IP, владелец домена свободен: всё остальное
делается на сервере.

## 1. Код и настройки

```bash
git clone https://github.com/A-blessed/MAX-olymp.git
cd MAX-olymp
cp .env.example .env
```

В `.env` заполнить:

| Переменная        | Значение                                            |
|-------------------|-----------------------------------------------------|
| `BOT_TOKEN`       | токен бота                                          |
| `BOT_USERNAME`    | ник бота без `@`                                    |
| `WEBHOOK_SECRET`  | произвольная строка 5–256 символов `[A-Za-z0-9_-]`  |
| `POSTGRES_PASSWORD` | не `app`: база хоть и не публикуется наружу, пароль из примера в проде не место |
| `CERTBOT_EMAIL`   | почта для писем об истечении сертификата            |

`PUBLIC_BASE_URL=https://my-olymp.ru` и `CORS_ORIGINS=https://my-olymp.ru`
уже стоят в шаблоне — менять их не нужно.

`APP_ENV` из `.env` в проде не читается: `docker-compose.prod.yml` жёстко
ставит `production`, иначе схема API открылась бы наружу молча.

Сертификаты Минцифры положить в `certs/` — без них бэкенд не установит
TLS-соединение с `platform-api2.max.ru`. Это отдельная история от
сертификата домена, они не взаимозаменяемы:

| Сертификат          | Зачем                                    | Откуда           |
|---------------------|------------------------------------------|------------------|
| Минцифры, `certs/`  | бэкенд → `platform-api2.max.ru`          | Госуслуги        |
| Let's Encrypt       | браузер и MAX → `my-olymp.ru`            | certbot, шаг 2   |

## 2. Сертификат домена

Курица и яйцо: nginx не поднимется без файла сертификата, а certbot не
сможет подтвердить домен через nginx, пока тот не поднялся. Поэтому
**первый** выпуск делается в режиме `--standalone`, когда порт 80 ещё
свободен, — то есть до первого `up`:

```bash
docker compose -f docker-compose.prod.yml run --rm -p 80:80 \
  --entrypoint certbot certbot \
  certonly --standalone --non-interactive --agree-tos \
  --email ВАША@ПОЧТА --no-eff-email \
  -d my-olymp.ru -d www.my-olymp.ru
```

Если A-записи для `www` нет — уберите `-d www.my-olymp.ru`, иначе выпуск
упадёт на проверке домена. В этом случае удалите и серверный блок `www`
из [`deploy/nginx/my-olymp.ru.conf`](../deploy/nginx/my-olymp.ru.conf):
без сертификата на `www` он отдаёт браузеру ошибку.

Сертификат ложится в том `letsencrypt` — не в репозиторий: закрытый ключ
не должен попасть в git даже случайно.

**Продление автоматическое.** Сервис `certbot` дважды в сутки вызывает
`renew` (до истечения срока больше 30 дней он ничего не делает), а nginx
раз в сутки перечитывает конфигурацию и подхватывает новый файл без
перезапуска и без обрыва соединений.

## 3. Запуск

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Поднимутся четыре сервиса: `db`, `backend`, `nginx`, `certbot`. Схему базы
Alembic применяет сам при старте бэкенда.

Наполнить каталог:

```bash
docker compose -f docker-compose.prod.yml run --rm backend python -m scripts.import_subjects
docker compose -f docker-compose.prod.yml run --rm backend python -m scripts.import_catalog
```

Проверить снаружи:

```bash
curl https://my-olymp.ru/health
```

Ожидается `{"status":"ok","env":"production","bot_configured":true,"webhook_secret_set":true}`.
Оба флага должны быть `true` — если нет, `.env` не доехал до контейнера.

И что отдаётся само приложение:

```bash
curl -I https://my-olymp.ru/
```

## 4. Подписка на события бота

Адрес вебхука сменился с туннельного на постоянный, поэтому подписку
нужно оформить заново — старая продолжает указывать на ngrok:

```bash
docker compose -f docker-compose.prod.yml run --rm backend python -m scripts.setup_webhook
```

Проверить, что осталась только одна подписка и она на новый адрес:

```bash
docker compose -f docker-compose.prod.yml run --rm backend python -m scripts.setup_webhook --list
```

Если в списке остался туннельный адрес, удалить его:

```bash
docker compose -f docker-compose.prod.yml run --rm backend \
  python -m scripts.setup_webhook --delete --url https://СТАРЫЙ-АДРЕС/webhook
```

Это важнее, чем кажется: пока подписка висит на мёртвом адресе, MAX
считает события недоставленными, а через 8 часов неудач отписывает бота
сам.

## 5. Адрес мини-приложения в кабинете MAX

**Через код этого сделать нельзя** — в Bot API нет такого метода. Только
в кабинете партнёров: **Чат-боты** → нужный бот → **⋮** →
**Настройки** → поле URL мини-приложения:

```
https://my-olymp.ru
```

Пока там стоит адрес GitHub Pages, MAX будет открывать старую копию
приложения, и никакие изменения на сервере на это не повлияют. Если
доступа к кабинету нет — адрес нужно передать организаторам.

## Если запускаете без Docker

Так тоже можно, но тогда всё, что compose делал за вас, придётся задать
руками. Пропущенное проявляется не при старте, а на первом запросе.

**Рабочий каталог решает.** Файл `.env` ищется относительно каталога, из
которого запущен процесс, а не рядом с кодом. Запускаете из `C:\Server` —
файл должен лежать в `C:\Server\.env`. С версии, где появился этот раздел,
приложение само пишет в лог полный путь, по которому искало.

Проверить, что файл вообще есть и назван правильно:

```
dir /a C:\Server\.env
```

`dir` без `/a` скрытые файлы не показывает. Если видно `.env.txt` — это и
есть причина: «Блокнот» дописывает расширение, а такой файл не читается.
Переименовать можно так:

```
ren C:\Server\.env.txt .env
```

**Не создавайте файл через `>` в PowerShell.** `... > .env` и `Out-File`
в Windows PowerShell 5.1 пишут UTF-16, и приложение падает на старте с
`UnicodeDecodeError`. Надёжнее из `cmd`:

```
cd /d C:\Server
(echo BOT_TOKEN=ваш_токен)>.env
```

Всё остальное файл переживает: переводы строк CRLF, BOM, кавычки вокруг
значения и пробелы вокруг `=` разбираются правильно. Пути Windows можно
писать как есть: `EXTRA_CA_CERTS_DIR=C:\Server\certs`.

**Что задать помимо токена.** Значения по умолчанию рассчитаны на Docker и
вне его не работают:

| Переменная | Значение по умолчанию | Почему не подойдёт |
|---|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://app:app@db:5432/app` | хост `db` существует только в сети compose; нужен адрес вашей Postgres — см. ниже |
| `EXTRA_CA_CERTS_DIR` | `certs` | подойдёт как есть, если каталог `certs\` лежит рядом с рабочим |
| `APP_ENV` | `development` | на публичном сервере открывает `/docs` и `/openapi.json` |

Без первой переменной API отвечает ошибкой подключения к базе, без второй
запросы к `platform-api2.max.ru` падают на TLS.

**Postgres нужна настоящая, SQLite не подойдёт.** В моделях каталога
используется тип `JSONB`, он есть только в Postgres; миграции написаны под
неё же. Порядок на Windows:

1. Поставить PostgreSQL для Windows. В compose стоит 16
   (`postgres:16-alpine`), но 17 работает так же — версия важна только
   тем, что от неё зависит путь к утилитам. В окне выбора компонентов
   нужны два:

   | Компонент | Нужен | Зачем |
   |---|---|---|
   | PostgreSQL Server | да | собственно база |
   | Command Line Tools | да | `psql`, `createdb` — ими делаются шаги ниже |
   | pgAdmin 4 | по желанию | графический клиент, ~500 МБ; для запуска не нужен |
   | Stack Builder | нет | загрузчик расширений вроде PostGIS, ничего из него не требуется |

   В мастере: каталоги оставить по умолчанию, пароль пользователю
   `postgres` — **только буквы и цифры** (`@`, `:`, `/`, `?` пришлось бы
   кодировать в строке подключения). На последнем шаге снять галочку
   запуска Stack Builder.

   **Запомните порт.** Обычно 5432, но если он занят — например, уже стоит
   другая версия Postgres, — установщик молча предложит 5433. Этот номер
   дальше нужен и в командах `createdb`/`psql` (ключ `-p`), и в
   `DATABASE_URL`. Посмотреть, кто занимает порты:

   ```powershell
   Get-NetTCPConnection -LocalPort 5432,5433 -State Listen | Select-Object LocalPort, OwningProcess
   ```

2. Добавить утилиты Postgres в PATH текущей сессии — тогда их можно
   вызывать по имени, и команды ниже одинаковы в PowerShell и в `cmd`.
   Номер версии подставьте свой, по имени созданной папки:

   ```powershell
   $env:Path += ";C:\Program Files\PostgreSQL\17\bin"
   ```

   Без этого в PowerShell команда, начинающаяся с кавычки, не запустится:
   он примет её за строку и ответит «Непредвиденная лексема». Вызвать
   файл по полному пути там можно только через оператор `&`:
   `& "C:\Program Files\...\createdb.exe" -U postgres ...`.

3. Создать базу — **обязательно с явной кодировкой UTF-8**:

   ```powershell
   createdb -U postgres -E UTF8 -T template0 --locale-provider=icu --icu-locale=ru-RU max_olymp
   ```

   Спросит пароль пользователя `postgres` — тот, что задали при установке.

   На русской Windows кластер создаётся в системной локали, и без этих
   ключей база получилась бы в WIN1251 — русские названия олимпиад в ней
   поехали бы. `--icu-locale=ru-RU` заодно даёт правильную сортировку: в
   каталоге `ORDER BY name` выполняет сама база.

   Если сборка без ICU и команда откажет, сработает вариант попроще, с
   сортировкой по байтам (кириллица упорядочится верно, но заглавные
   окажутся впереди строчных):

   ```powershell
   createdb -U postgres -E UTF8 -T template0 --locale=C max_olymp
   ```

   Проверить, что вышло:

   ```powershell
   psql -U postgres -l
   ```

   В строке `max_olymp` должно стоять `UTF8`. Если там `WIN1251` — базу
   нужно удалить (`dropdb -U postgres max_olymp`) и создать заново, пока
   каталог в неё не импортирован.
4. Прописать в `.env`:

   ```
   DATABASE_URL=postgresql+asyncpg://postgres:пароль@localhost:5432/max_olymp
   ```

   Порт в строке — тот, что выбрал установщик. Если 5433, то и здесь 5433.

   **`POSTGRES_PORT` для этого не годится**: её читает только
   docker-compose, чтобы опубликовать порт контейнера на хост. Приложение
   её не смотрит вовсе — адрес базы оно берёт целиком из `DATABASE_URL`.

   Если в пароле есть `@`, `:`, `/` или `?`, их нужно закодировать
   (`@` → `%40`): иначе строка разберётся неправильно. Проще задать пароль
   из букв и цифр.

   Проверить, что приложение читает именно то, что нужно, можно по логу
   старта: он печатает строку подключения целиком, с портом и без пароля.
5. Создать схему и наполнить каталог, из `C:\Server`:

   ```
   alembic upgrade head
   python -m scripts.import_subjects
   python -m scripts.import_catalog
   ```

Связь с базой проверяется при старте: в логе будет либо «База … отвечает»,
либо причина отказа. Пароль в лог не попадает.

**Сертификаты кладите в `certs\` рядом с рабочим каталогом** — то есть
`C:\Server\certs\`, а не `C:\Server\app\certs\`. Годятся только файлы с
расширением `.crt`, `.pem` и `.cer`; связку `.p7b` с Госуслуг нужно сначала
разобрать на отдельные сертификаты. Лог старта перечисляет, что подхватил,
а если не подхватил ничего — пишет полный путь, где искал.

**Статику приложение отдаёт само — если найдёт.** Положите каталог
`frontend/` рядом с рабочим каталогом, из которого запускаете:

```
C:\Server\
├── app\          код приложения
├── frontend\     файлы мини-приложения
└── .env
```

Тогда `GET /` вернёт `index.html`, и в MAX приложение откроется. Каталог
ищется по `FRONTEND_DIR` (по умолчанию `frontend`, путь от рабочего
каталога). В лог старта пишется, нашёлся он или нет.

Если каталога нет, раздача выключается и корень отвечает `404` — это
нормально для Docker, где статику отдаёт nginx, но при запуске без него
означает, что мини-приложение не откроется вовсе.

Отдаётся с `Cache-Control: no-cache`: встроенный браузер MAX иначе держит
старую версию и после выкладки.

**Быстрая проверка, что токен доехал** — не заглядывая в файл:

```
curl https://my-olymp.ru/health
```

Поле `bot_configured` должно быть `true`. Если `false` — процесс токена не
видит, и смотреть надо в лог старта: там теперь написано, какой именно
файл искали и нашли ли.

Чтобы отделить «токен неверный» от «файл не читается», задайте переменную
прямо в сессии и перезапустите — переменная окружения имеет приоритет над
файлом:

```
set BOT_TOKEN=<токен>
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Предупреждение про `BOT_TOKEN` пропало — значит дело было в файле.

### HTTPS без Docker: Caddy

Всё описанное выше поднимает **бэкенд**, и на этом останавливается. А
MAX доставляет события только по https на 443 и не принимает
самоподписанные сертификаты, так что без TLS мини-приложение не
откроется, а бот не получит ни одного события.

В Docker этим занимались nginx и certbot — оба контейнерами. Без Docker
их надо чем-то заменить, и проще всего [Caddy](https://caddyserver.com):
одна программа вместо двух, сертификат Let's Encrypt выпускается при
первом запуске и продлевается сам, без webroot и заданий в планировщике.

Готовая конфигурация лежит в [`deploy/Caddyfile`](../deploy/Caddyfile) —
она повторяет то, что делает наш nginx: статика мини-приложения, прокси
на `/api/*`, `/webhook`, `/health` и схему API, перенаправление с `www`,
заголовки безопасности и запрет кэширования статики.

**Что нужно до запуска:**

* A-запись домена указывает на эту машину (шаг 0);
* порты 80 и 443 свободны и открыты в брандмауэре. Порт 80 нужен не
  только для перенаправления — по нему Let's Encrypt подтверждает
  владение доменом. На Windows Server его часто занимает IIS: проверьте
  `Get-Service W3SVC`;
* бэкенд слушает `127.0.0.1:8000` и наружу не смотрит.

**Порядок:**

1. Скачать `caddy.exe` с [caddyserver.com/download](https://caddyserver.com/download)
   и положить, например, в `C:\Caddy`.
2. Скопировать туда `deploy/Caddyfile`.
3. Поправить в нём два места: путь в строке `root *` — он должен вести
   на каталог `frontend` вашего клона, — и почту в `email`.
4. Запустить:

   ```powershell
   cd C:\Caddy
   .\caddy.exe run --config Caddyfile
   ```

При первом запуске Caddy сходит в Let's Encrypt за сертификатом; в
выводе появятся строки про `certificate obtained successfully`. После
этого `https://my-olymp.ru/health` должен отвечать тем же, чем и
`http://127.0.0.1:8000/health`.

Перенаправление с http на https Caddy включает сам — отдельный
серверный блок на 80, как в nginx, писать не нужно.

Заголовки в блоке `handle` дополняют заголовки уровня сайта, а не
заменяют их: в отличие от nginx, повторять `Strict-Transport-Security`
и `X-Content-Type-Options` во вложенном блоке не требуется.

`caddy run` держит окно занятым и умирает вместе с сеансом RDP. Для
постоянной работы Caddy нужно запускать службой — через обёртку вроде
NSSM или заданием планировщика «При запуске компьютера».

## Обновление кода

```bash
git pull
docker compose -f docker-compose.prod.yml up -d --build backend
```

Фронтенд подключён к nginx томом, а не вложен в образ: правки в
`frontend/` доезжают одним `git pull`, пересобирать ничего не нужно.
Статика отдаётся с `Cache-Control: no-cache`, иначе встроенный браузер
MAX держал бы старую версию и после деплоя.

## Если что-то не работает

### Сначала — один снимок состояния

Половина поломок деплоя видна не в той строке, на которую смотришь, а в
соседней: в дате сертификата, в чужом IP у домена, в том, что контейнер
не поднялся вовсе. Пересказывать такое по кускам — долго и ненадёжно,
поэтому состояние снимается целиком одной командой, на самой машине:

```bash
bash deploy/diagnose.sh
```

На Windows, где Docker не ставится, — та же команда в PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File deploy\diagnose.ps1
```

`-ExecutionPolicy Bypass` нужен почти всегда: на Windows Server запуск
скриптов закрыт по умолчанию, и без ключа команда молча откажет.
Политику он меняет только для этого запуска.

Скрипт ничего не меняет и не перезапускает — только читает. Он собирает
в один файл `diagnostics-<дата>.txt`: версию кода, заданные переменные
окружения, состояние сервисов и их логи, срок и домены сертификата, кто
слушает 80 и 443, куда ведёт DNS и что отвечает сайт — снаружи и в обход
DNS.

Версия для Windows проверяет вдобавок то, что бывает только там:
кодировку `.env` (UTF-16 от `Out-File` — та самая причина
`UnicodeDecodeError` на старте), службу PostgreSQL, занят ли порт 80
службой IIS и есть ли в брандмауэре разрешающие правила на 80 и 443.

Файл сделан пригодным для пересылки: `BOT_TOKEN`, `WEBHOOK_SECRET`,
`POSTGRES_PASSWORD` и `CERTBOT_EMAIL` в нём заменены на `<скрыто>` — и в
самом `.env`, и в логах, куда могли просочиться. Его можно показывать
целиком, не вычитывая.

Таблица ниже — что искать в этом файле.

| Симптом | Где смотреть |
|---|---|
| `nginx: host not found in upstream "backend"` | бэкенд не стал healthy; `docker compose -f docker-compose.prod.yml logs backend` |
| 502 на `/api/*` | бэкенд упал или ещё применяет миграции; те же логи |
| 404 на `/docs` | так и задумано: `APP_ENV=production` закрывает схему |
| Приложение открылось, но данные не грузятся | адрес в кабинете MAX ведёт не на `my-olymp.ru`, либо origin не совпал — сверьте адрес в строке браузера с `BASE_URL` в `frontend/api.js` |
| Бот не отвечает | подписка указывает на старый адрес; шаг 4 |
| Ошибка сертификата на `www` | сертификат выписан без `www`; либо добавьте его в certbot, либо удалите блок `www` из конфига nginx |
| `Address family not supported by protocol` в логах nginx | на хосте отключён IPv6, а в конфиге появились строки `listen [::]` |
| Certbot: `DNS problem` или `Invalid response` | домен ещё не указывает на сервер или порт 80 закрыт; шаг 0 |
| Домен открывает страницу регистратора | не снята парковка или включено перенаправление домена; шаг 0 |
| Сайт открывается через раз | лишняя `AAAA`-запись: браузер идёт по IPv6, а nginx слушает IPv4; шаг 0 |
| `BOT_TOKEN не задан` при живом `.env` | процесс запущен не из той папки или файл назван `.env.txt`; лог старта печатает путь, по которому искали |
| `404` на `/` при работающем `/api` | рядом с рабочим каталогом нет `frontend/`; лог старта пишет, где искали |
| В MAX вместо приложения `404` | то же самое: корень домена не отдаёт `index.html` |
| `500` на `/api/*`, в трейсбеке `getaddrinfo failed` | `DATABASE_URL` ведёт на хост `db` из Docker; лог старта пишет это отдельной строкой |
| `ConnectionRefusedError` вместо `getaddrinfo` | хост верный, а порт нет: установщик мог занять 5433; сверьте с логом старта |
| «В каталоге … нет сертификатов», хотя они там | смотрите путь в самом сообщении: он абсолютный и говорит, куда приложение смотрело на самом деле |
