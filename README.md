# Мини-приложение и чат-бот MAX

## Назначение продукта

Продукт создан специально для национального мессенджера MAX: чат-бот и мини-приложение.

Сейчас массовых решений для отслеживания олимпиад нет: есть только календари, куда данные приходится вносить вручную. По результатам нашего опроса, более 75% учащихся пропускали этапы олимпиад из-за сложности отслеживания сроков, и примерно столько же хотели бы иметь для этого удобное мини-приложение.

Целевая аудитория продукта — учащиеся 5–11 классов, участвующие или желающие участвовать в олимпиадах.

Продукт автоматически отслеживает изменения в данных об олимпиадах (название, уровень, даты и др.), которые берутся с портала [Olimpiada.ru](https://olimpiada.ru), составляет индивидуальный календарь, помогающий отслеживать сроки олимпиад, а также присылает напоминания о ближайших этапах. Пользователю достаточно указать класс и отметить олимпиады, в которых он участвует.

Так олимпиадники не пропустят этапы из-за забытых сроков: вся информация и напоминания приходят в привычный мессенджер.

## Основной пользовательский сценарий

Авторизованный в MAX пользователь заходит в мини-приложение и выбирает класс (5–11). 

Далее он попадает на .......

## Состав и архитектура

В решении три части: бэкенд на FastAPI, мини-приложение на JavaScript без сборки и база Postgres. Бэкенд в одном процессе обслуживает API мини-приложения, вебхук бота и ежедневную рассылку. Всё работает на одном домене за nginx:

```
пользователь в MAX
        │
        ▼
nginx :443, my-olymp.ru
        ├── /           статика мини-приложения из frontend/
        ├── /api/*   ─┐
        ├── /webhook ─┼──►  FastAPI (backend/)  ──►  Postgres
        └── /health  ─┘            │
                                   └──►  platform-api2.max.ru: сообщения бота
```

### Что есть в приложении

В мини-приложении четыре вкладки и окно настроек:

| Экран | Что там | API |
|---|---|---|
| Поиск | предметы с числом олимпиад для класса пользователя, список олимпиад по предмету, карточка олимпиады с этапами и кнопкой «Буду писать» | `GET /api/catalog/subjects`, `GET /api/catalog/olympiads`, `GET /api/catalog/olympiads/{id}` |
| Новости | события по сохранённым олимпиадам: «Появились даты», «Срочно», «Скоро», «Позже», «Ожидает ответа от тебя» | `GET /api/me/news` |
| Мои | сохранённые олимпиады и ответы «прошёл / не прошёл» по этапам | `GET /api/me/olympiads`, `POST` и `DELETE /api/me/olympiads/{id}`, `PUT` и `DELETE /api/me/stages/{id}/result` |
| Календарь | этапы на сетке месяца и план — какой этап в какой день писать | `GET /api/me/calendar`, `GET /api/me/calendar/{day}`, `PUT` и `DELETE /api/me/stages/{id}/plan` |
| Настройки | класс, уведомления, режим для дальтоников | `GET` и `PATCH /api/me/settings` |

Правила механики проверяет сервер, в [`personal/rules.py`](backend/app/personal/rules.py):

* на один день можно запланировать не больше трёх олимпиад;
* этап ставится в календарь только на свои даты; если у этапа известен только дедлайн, то на любой из 14 дней перед ним;
* после ответа «не прошёл» следующие этапы олимпиады закрываются, их планы и ответы удаляются.

Если действие нарушает правило, сервер отвечает `409` или `422` с кодом ошибки, и фронтенд выбирает реакцию по коду. Все поля и коды описаны в [docs/api-for-frontend.md](docs/api-for-frontend.md).

Бот делает три вещи: на запуск присылает приветствие с кнопкой открытия приложения, на любое сообщение отвечает той же кнопкой и раз в день присылает сводку по сохранённым олимпиадам (см. «Утренняя сводка» ниже).

### Два контура аутентификации

| Контур           | Кто обращается | Как подтверждает себя                       |
|------------------|----------------|---------------------------------------------|
| `POST /webhook`  | платформа MAX  | заголовок `X-Max-Bot-Api-Secret`            |
| `/api/*`         | мини-приложение| подпись данных запуска в `Authorization`    |

Секрет вебхука бэкенд передаёт MAX сам, при подписке на события (`scripts.setup_webhook`). Проверка подписи для мини-приложения описана ниже.

### Почему бот и API в одном сервисе

MAX принимает вебхук только по HTTPS на порту 443 и с сертификатом доверенного центра. Если разнести бота и API по разным сервисам, понадобятся два публичных адреса и два сертификата. Поэтому сервис один, а `bot/` и `api/` разделены только в коде: при необходимости их можно развести, не переписывая логику.

Мини-приложение отдаётся с того же домена, что и API. Запросы идут на свой origin, поэтому в проде нет ни preflight, ни CORS. TLS на 443 делает nginx из [`deploy/nginx/`](deploy/nginx/), само приложение слушает обычный HTTP.

### Проверка данных запуска

MAX передаёт мини-приложению подписанную строку запуска, а фронтенд отправляет её на сервер в заголовке `Authorization: tma <initData>`. Подпись считается от токена бота, поэтому проверить её может только сервер.

Алгоритм взят из [документации MAX](https://dev.max.ru/docs/webapps/validation), реализация — в [`launch_data.py`](backend/app/security/launch_data.py):

1. строка разбирается на пары, каждый ключ должен встречаться ровно один раз (иначе через дубликат можно подсунуть значение в обход подписи);
2. `hash` откладывается отдельно и в подписываемые данные не входит;
3. значения URL-декодируются, пары сортируются по ключу и склеиваются через `\n`;
4. `secret_key = HMAC-SHA256(key="WebAppData", msg=BOT_TOKEN)`;
5. `hash = hex(HMAC-SHA256(key=secret_key, msg=launch_params))`;
6. результат сравнивается с присланным `hash` в постоянном времени.

Ещё проверяется `auth_date`: строка старше `LAUNCH_DATA_TTL` отклоняется, чтобы перехваченная строка не работала вечно. `initDataUnsafe` сервер не использует, его можно подделать. Идентификатор пользователя берётся только из проверенной строки и никогда из тела запроса.

### Олимпиада по предмету

Уровень по перечню РСОШ зависит от предмета: Московская олимпиада школьников по астрономии — I уровня, по истории — II. В текущем каталоге 34 олимпиады проходят сразу по нескольким предметам, и у 5 из них уровень разный.

Поэтому одна запись в каталоге — это пара «олимпиада + предмет». Описание, сайт, классы и организаторы у всех предметов одной олимпиады одинаковые и просто дублируются. «Ломоносов» встречается в каталоге 13 раз, олимпиада СПбГУ — 12, и в «Мои олимпиады» они тоже добавляются по предмету.

### Миграции

Схему ведёт Alembic. Бэкенд применяет миграции сам при старте, до запуска HTTP-сервера, так что одна команда поднимает и пустую базу, и существующую. Потом `scripts.seed` заполняет каталог из `backend/data/`, если он пустой, а непустой не трогает.

После изменения моделей:

```bash
docker compose run --rm backend alembic revision --autogenerate -m "что меняем"
```

Файл появится в `backend/migrations/versions/`. Его нужно просмотреть и закоммитить, применится он при следующем старте.

### Точность дат

Приложение считает «до этапа N дней», рисует календарь по дням и присылает сводку о событиях дня. Для этого нужен точный день, а он известен не всегда. Расписание с olimpiada.ru даёт дни, а в выгрузке postupi.online у 32 этапов из 97 есть только месяц и год («мар 2027»). Если считать по такой дате дни, получится правдоподобное, но выдуманное число.

Поэтому у каждой даты хранится её точность, и API отдаёт её явно:

| Поле | Смысл |
|---|---|
| `start_precision` | `day` — известен день, `month` — только месяц |
| `days_until_start` | число дней или `null`, если точного дня нет |
| `plannable` | `false` — этап нельзя поставить в календарь |
| `raw_date_range` | исходная строка источника, например «мар 2027» |

Если `days_until_start` равен `null`, фронтенд не показывает таймер и выводит `raw_date_range` как есть. Как этап рисуется в календаре (полоса, кружок или дедлайн), описано в разделе «Форма сроков этапа».

Тип этапа (`kind`: регистрация, отборочный, финал) определяется по названию, в источнике его нет. Если определить не получилось, ставится `other`; в расписании таких 16 этапов из 147.

### Лента «Новости»

Ленту сервер не хранит, а считает при каждом запросе из дат этапов и ответов пользователя ([`personal/news.py`](backend/app/personal/news.py)). Так она не может разойтись с календарём, когда даты в источнике меняются.

| Категория | Что в ней |
|---|---|
| Срочно | этап начинается или заканчивается сегодня |
| Скоро | начинается или заканчивается в ближайшие 7 дней |
| Позже | всё остальное впереди |
| Ожидает ответа от тебя | этап закончился, а ответа «прошёл / не прошёл» нет |
| Появились даты | у этапа появились даты, пока олимпиада была в «Моих» |

Каждый этап попадает ровно в одну из первых четырёх категорий (ещё есть «Завершённые», их интерфейс пока не показывает). «Появились даты» идёт поверх: этап с новыми датами остаётся и в своей категории. В «Срочно» и «Скоро» попадают только этапы с точным днём.

### Утренняя сводка

Раз в день, в `REMINDER_TIME`, бот присылает одно сообщение по всем олимпиадам, за которыми следит пользователь. Одно, а не по сообщению на событие: в сезон у школьника с пятью олимпиадами бывает по нескольку событий в день, и десяток уведомлений он просто выключит.

В сводку попадают только события с точным днём, у одного этапа — не больше одной строки:

| Блок | Что в нём |
|---|---|
| Сегодня | запланированный на сегодня этап, начало этапа, последний день |
| Завтра | то же про завтра |
| Через 3 дня | последний день этапа, чтобы успеть доделать работу |
| Как прошло? | этап закончился вчера, а ответа «прошёл / не прошёл» нет |

Если сказать нечего, сообщения не будет: пустые сводки приучают не открывать сообщения бота.

Сводку получают те, кто запустил бота (иначе MAX не даст ему писать), не выключил уведомления в настройках и сохранил хотя бы одну олимпиаду.

Время этапов в источнике не указано, только даты. Поэтому напоминания «за час до начала» нет, его заменяет сводка накануне и утром в день события.

Чтобы не написать человеку дважды, перед отправкой в `reminder_log` вставляется строка «пользователь + день», и первичный ключ не даёт вставить её второй раз. Бэкенд можно перезапускать: если он поднялся в 9:40 после сбоя, то допишет тем, кому не успел, а остальных не тронет. Если MAX недоступен, проход прерывается и повторяется через 10 минут. Ошибка по одному человеку (например, он удалил диалог) на остальных не влияет. После 21:00 рассылка не начинается.

Проверить на себе, не дожидаясь утра:

```bash
python -m scripts.send_reminders --users                     # найти свой id
python -m scripts.send_reminders --dry-run                   # что уйдёт сегодня, без отправки
python -m scripts.send_reminders --dry-run --date 2026-10-14 # как будто сегодня 14 октября
python -m scripts.send_reminders --user <id> --date 2026-10-14 --force
```

Если сводка кому-то не приходит, `--user <id>` покажет причину: от человека не было событий бота, уведомления выключены или нет сохранённых олимпиад. С `--dry-run` текст сводки выводится и в этом случае. Что бот уже отправил, записано в `reminder_log.text`.

О том, что человек запустил бота, сервер узнаёт только из событий MAX, а они приходят только при подписке на вебхук. При старте бэкенд проверяет подписку и пишет в лог «Подписка на события MAX: …», если всё в порядке, или «MAX не присылает события на …», если нужно запустить `python -m scripts.setup_webhook`. Событие `bot_started` приходит один раз, поэтому тех, кто запустил бота до подписки, сервер отметит по первому их сообщению боту.

## Запуск (ПРАВКИ)

### Что нужно заранее

* **Docker** с Compose **не ниже 2.24** — Docker Desktop на Windows и macOS, Docker Engine на Linux; проверить — `docker compose version`. Более старый Compose не понимает необязательный `.env` в `docker-compose.yml` и откажется запускать. Больше ничего ставить не нужно: Python, Postgres и nginx приезжают в образах.
* **Git** — требование к сдаче: нужен репозиторий с commit hash.
* Для работы бота, но не для запуска: **токен бота** — выдают организаторы хакатона, — и **сертификаты Минцифры** в `certs/`, см. [certs/README.md](certs/README.md). Без них запросы к API MAX падают с ошибкой TLS.

### Одна команда

```bash
docker compose up --build
```

Поднимаются три сервиса:

| Сервис    | Что это | Адрес |
|-----------|---------|-------|
| `db`      | Postgres 16 | `127.0.0.1:5432`, только для клиента БД |
| `backend` | API и бот; при старте применяет миграции и наполняет пустой каталог | `http://localhost:8000` |
| `web`     | nginx: мини-приложение и прокси `/api`, `/webhook`, `/health` в бэкенд | `http://localhost:8080` |

Каталог олимпиад наполняется сам при первом старте из выгрузок в `backend/data/` — после `up` приложение сразу с данными, импортировать руками ничего не нужно.

`.env` для запуска не обязателен: без него поднимается всё, только бот не знает своего токена. Для работы с MAX скопируйте шаблон и заполните `BOT_TOKEN`:

```bash
cp .env.example .env
```

В PowerShell:

```powershell
Copy-Item .env.example .env
```

### Остановка и повторный запуск

```bash
docker compose down
```

Данные Postgres лежат в именованном томе и переживают остановку — следующий `docker compose up` поднимет то же состояние.

Удалить данные вместе с контейнерами:

```bash
docker compose down -v
```

Перезапустить один сервис, не трогая базу:

```bash
docker compose restart backend
```

Пересобрать после изменения кода или зависимостей:

```bash
docker compose up --build
```

Локальный `docker-compose.yml` TLS не делает и слушает обычный HTTP. Для сервера есть отдельный файл — он собирает те же образы, но nginx получает сертификат Let's Encrypt и слушает 80 и 443, а порты бэкенда и базы с хоста убраны:

## Работа с данными

Хранятся только те данные, что приходят из проверенных данных запуска и событий бота:

* `users` — идентификатор в MAX, имя, ник, язык, ссылка на фото, метка запуска из диплинка, время первого и последнего визита;
* `bot_dialogs` — может ли бот писать пользователю (запустил он бота или остановил).

Каталог олимпиад:

* `olympiads` — название, ссылка на источник, вузы-партнёры, отметка о том, когда запись последний раз подтверждалась в источнике;
* `stages` — этапы с датами, точностью дат и предполагаемым типом;
* `subjects`, `categories` — справочники предметов и категорий.

Данные пользователя:

* `saved_olympiads` — что добавлено кнопкой «Буду писать»;
* `stage_progress` — ответы «прошёл / не прошёл» по этапам;
* `stage_plans` — какой этап на какой день запланирован в календаре;
* `user_settings` — класс, уведомления, режим для дальтоников.

Хранятся на сервере, а не в браузере: напоминания отправляет бот, и он должен знать, за чем следит пользователь, даже когда мини-приложение закрыто. Вкладка «Новости» отдельно не хранится — она вычисляется из дат этапов и ответов пользователя. Единственное, что для неё запоминается, — `stages.dates_added_at`: момент, когда импорт расписания увидел у этапа даты, которых раньше не было. Из него строится блок «Появились даты»: этапы обновляются на месте, и без отметки прошлое состояние не узнать.

Идентификатор пользователя записывается только после проверки подписи. Таблицы создаются автоматически при старте приложения, каталог при первом старте наполняется из `backend/data/`.

Персональные данные из внешних систем не обрабатываются.

### Источники данных

| Источник | Что даёт | Чего нет |
|---|---|---|
| `data/subjects.sample.json` | 166 записей: предметы, уровни, классы, описания, организаторы | этапов и дат |
| `data/olympiads_schedule.json` | 147 этапов с датами у 61 олимпиады | всего остального |
| `data/olympiads.sample.json` | 97 этапов у 20 олимпиад, другой источник | предмета и уровня |

Первый файл наполняет каталог, второй доставляет в него даты. До появления второго «Поиск» работал на каталоге, а «Календарь» и «Новости» — на третьем файле, чьи записи предмету не принадлежат и потому в интерфейсе не видны. Теперь даты приходят прямо в каталожные олимпиады, и обе вкладки работают на тех же записях, что и поиск.

Расписание снимается с olimpiada.ru отдельным парсером ([`tools/olympiad_schedule_parser.py`](tools/olympiad_schedule_parser.py)) и кладётся в базу командой `python -m scripts.import_schedule`. Связать его с каталогом напрямую нечем: парсер знает олимпиады по `activity_id` olimpiada.ru, а база — по `id` из каталога. Соответствие берётся из `data/subjects.olimpiada.json` — это тот же каталог, размеченный идентификаторами olimpiada.ru. Импортируется он не как каталог, а только как таблица соответствия.

Года в расписании на сайте нет — парсер угадывает его от даты запуска, и у диапазона год считается один раз, по концу: иначе «20 авг...22 сен», разобранный в сентябре, получал начало на год позже конца. Разбор дат проверяют тесты рядом с парсером (`cd tools && python -m pytest`), а файлы, снятые до исправления, импорт выправляет сам.

Расписание есть не у всех: на olimpiada.ru его нет у 85 олимпиад из 146. Записи разных источников различаются полем `source` и друг другу не мешают.

#### Форма сроков этапа

Парсер размечает сроки четырьмя способами, и каждый рисуется в календаре по-своему. В базе для этого нет отдельного поля: всё выражено тем, какие из дат заполнены, а обратно значение вычисляет `presentation.date_precision` и отдаёт в API полем `date_precision`.

| Значение | `starts_on` | `ends_on` | Как показывать |
|---|---|---|---|
| `range` | начало | конец | непрерывная полоса цвета предмета |
| `exact` | день | — | кружок в цвет олимпиады |
| `until` | — | дедлайн | полоса, набирающая непрозрачность к последнему дню |
| `unknown` | — | — | в календаре не показывать |

Таблица — о том, как даты лежат в базе. Наружу их отдаёт `presentation.stage_bounds` в полях парсера: у `exact` конец равен началу, поэтому карточка этапа и календарь показывают одни и те же даты.

Вычисление, а не хранение, выбрано намеренно: значение не может разойтись с датами, по которым посчитано. Дата с точностью до месяца попадает в `unknown` — конкретного дня у неё нет, а календарь размечает дни; сама точность при этом остаётся в `start_precision` и `raw_date_range`.

### Порядок работы с тестовыми данными

Все выгрузки лежат в `backend/data/` и едут в образе — проверка решения не требует ручного подкладывания файлов. При первом старте бэкенд сам импортирует их в пустой каталог (`scripts.seed`). Обновить данные в уже наполненной базе — те же импорты по отдельности:

```bash
docker compose run --rm backend python -m scripts.import_subjects
docker compose run --rm backend python -m scripts.import_schedule
docker compose run --rm backend python -m scripts.import_catalog
```

`import_schedule` не пропускайте: без него у олимпиад каталога нет дат, и «Календарь» с «Новостями» пусты.

Импорт идемпотентен: повторный запуск обновляет записи на месте, а не дублирует их. Обновление на месте принципиально — прогресс пользователя по этапам ссылается на строки таблицы `stages`, и пересоздание обнуляло бы его при каждом обновлении данных.

Данные собраны парсером с `postupi.online` и являются срезом на момент выгрузки. Дата последней проверки записи отдаётся в поле `source_checked_at`.

## Пошаговый сценарий проверки (ПРАВКИ)

**1. Подготовка**

```bash
cp .env.example .env
```

Заполните `BOT_TOKEN`, положите сертификаты в `certs/`. Шаги 2, 3, 5 и 7 проходят и без этого, шагам 6 и 8 хватит любого непустого `BOT_TOKEN`: строку запуска подписывает и проверяет один и тот же токен.

**2. Запуск**

```bash
docker compose up --build
```

В логе бэкенда — применённые миграции и «Каталог пуст — импортируем выгрузки из data/» со счётчиками.

**3. Живость сервиса**

```bash
curl http://localhost:8080/health
```

Тот же ответ и напрямую, в обход nginx: `http://localhost:8000/health`. Мини-приложение открывается на `http://localhost:8080/` — вне MAX у него нет строки запуска, поэтому данные в нём не загрузятся; API с подписью проверяется на шаге 6.

Ожидается:

```json
{"status":"ok","env":"development","bot_configured":true,"webhook_secret_set":true}
```

**4. Связь с API MAX**

```bash
docker compose run --rm backend python -m scripts.check_connection
```

Скрипт печатает подхваченные сертификаты и ответ `GET /me`. Здесь же видно ник бота — его стоит прописать в `BOT_USERNAME`.

**5. Тесты**

```bash
docker compose --profile test run --rm tests
```

Проверяются валидные данные запуска, подделанный идентификатор, чужой токен, просроченный `auth_date`, дубликат параметра, а также соответствие разбора официальному примеру из документации и соблюдение лимита отправки.

**6. API мини-приложения без самого MAX**

Генератор подписывает строку запуска вашим токеном, поэтому сервер принимает её как настоящую:

```bash
docker compose run --rm backend python -m scripts.make_launch_data --curl
```

Выполните напечатанную команду — `GET /api/me` вернёт профиль.

**7. Каталог олимпиад**

Наполняется сам при первом старте — в логе бэкенда:

```bash
docker compose logs backend | grep data/
```

Ожидается по выгрузкам: `subjects.sample.json` — `subjects_created: 14`, `olympiads_created: 166`; `olympiads_schedule.json` — 150 этапов у 62 олимпиад; `olympiads.sample.json` — `olympiads_created: 20`, `stages_created: 97`. Дальше список доступен по `GET /api/catalog/olympiads`, детали — по `GET /api/catalog/olympiads/{id}`; оба требуют того же заголовка `Authorization: tma <initData>`. Без расписания `GET /api/me/calendar` отдаёт пустой `entries` при любых сохранённых олимпиадах.

**8. Пользовательский сценарий целиком**

```bash
docker compose run --rm backend python -m scripts.smoke_test
```

Скрипт проходит механику от лица тестового пользователя: «Буду писать», планы в календаре, лимит трёх олимпиад в день, ответ «не прошёл» с блокировкой следующих этапов, новости, настройки и удаление. Ожидается `провалено 0`. Данные тестового пользователя удаляются после прогона.

**9. Вебхук**

В `PUBLIC_BASE_URL` уже стоит `https://my-olymp.ru`. Если проверяете на своей машине, подставьте туда адрес туннеля — MAX не доставит события на `localhost`. Туннель направляйте на порт 8080: там на одном адресе и вебхук, и мини-приложение. Затем:

```bash
docker compose run --rm backend python -m scripts.setup_webhook
```

Напишите боту в MAX — в логах `docker compose logs -f backend` появится событие, а бот ответит в чат.

## Известные ограничения

* **Сессии не заводятся.** Подпись проверяется на каждом запросе, срок жизни строки запуска ограничен `LAUNCH_DATA_TTL` (по умолчанию сутки). После истечения фронтенд должен переоткрыть мини-приложение.
* **Рассылка живёт в процессе бэкенда.** Отдельной службы нет, поэтому если бэкенд лежит с утра до 21:00, сводка в этот день не уйдёт. Двойной отправки при нескольких процессах не будет — замок в базе, — но рассылать будет только один из них.
* **Очередь отправки живёт в памяти процесса.** При нескольких репликах бэкенда лимит 2 сообщения в секунду перестанет соблюдаться — понадобится общий счётчик, например в Redis.
* **Повторная доставка событий не отслеживается.** При неудачном ответе MAX повторяет доставку до 10 раз, и одно событие может обработаться дважды. Обработчики, меняющие состояние, стоит делать идемпотентными.
* **Данные собраны из двух источников.** У записей с предметами нет этапов, у записей с этапами нет предмета — см. «Два источника данных».
* **Категорий и подкатегорий пока нет.** Механика предполагает уровень «категория → подкатегория → предмет»; в данных есть только предметы, таблица категорий пустая.
* **Тип этапа — эвристика по названию**, а не данные источника.
* **Треть этапов не имеет точного дня начала** — для них недоступны таймеры, календарь по дням и утренние напоминания.
* **Источник бывает недоступен.** Приложение работает на сохранённых данных; дата последней проверки видна в `source_checked_at`.
* **Отмена ответа «не прошёл» не восстанавливает планы.** При этом ответе планы и ответы по следующим этапам удаляются; после отмены их нужно поставить заново.
* **Правила механики — в одной точке.** Лимит «три в день» и блокировки проверяются на сервере; интерфейс может их не дублировать, но должен показывать ответ сервера.
* **Публичный адрес нужен даже для отладки вебхука.** MAX не доставляет события на `localhost`: либо сервер на `my-olymp.ru`, либо туннель.
* **`CORS_ORIGINS` — список, а не `*`.** В бою фронтенд и API на одном origin, и CORS не участвует; звёздочка понадобилась бы только для копии страницы на стороннем адресе.
* **Long Polling не поддерживается** сознательно: для продакшена документация требует вебхук, а при активной подписке Long Polling всё равно не работает.

## Особенности платформы MAX

То, на чём мы уже спотыкались:

* ботов обслуживает только `platform-api2.max.ru`, старый `platform-api.max.ru` для них не работает;
* токен передаётся только в заголовке `Authorization`, без `Bearer` и не в query;
* без сертификата Минцифры в доверенных любой запрос падает с ошибкой TLS;
* вебхук работает только по HTTPS на 443, самоподписанные сертификаты MAX не принимает;
* на вебхук нужно ответить 200 в течение 30 секунд, иначе событие считается недоставленным; если доставка не проходит 8 часов, бот отписывается автоматически;
* `GET /chats` удалён, список чатов теперь получают через `POST /subscriptions`;
* в payload диплинка допустимы только `A-Z a-z 0-9 _ -`, с пробелами или кириллицей параметр молча вырезается;
* документация часто меняется, перед релизом стоит заглянуть в [changelog API](https://dev.max.ru/docs-api/changelog-api) и [changelog платформы](https://dev.max.ru/docs/changelog-platform).
