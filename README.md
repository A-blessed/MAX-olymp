### Два контура аутентификации

Их легко перепутать, а это разные механизмы:

| Контур           | Кто обращается | Как подтверждает себя                       |
|------------------|----------------|---------------------------------------------|
| `POST /webhook`  | платформа MAX  | заголовок `X-Max-Bot-Api-Secret`            |
| `GET /api/*`     | мини-приложение| подпись данных запуска в `Authorization`    |

### Почему бот и API — один сервис

Вебхук обязан быть доступен по HTTPS на порту 443 с сертификатом
доверенного центра. Разносить бота и API по разным контейнерам значит
заводить два публичных адреса и два сертификата ради одного процесса.
Один домен — один туннель — один сертификат. Модули `bot/` и `api/`
разделены в коде, так что при необходимости их можно развести по
сервисам, не переписывая логику.

### Проверка данных запуска

Главная задача бэкенда. Мини-приложение получает от MAX подписанную
строку и присылает её на сервер; проверить подпись может только сервер,
потому что она считается на основе токена бота.

Алгоритм — [dev.max.ru/docs/webapps/validation](https://dev.max.ru/docs/webapps/validation),
реализация в [`launch_data.py`](backend/app/security/launch_data.py):

1. параметры разбираются на пары, каждый ключ обязан встречаться ровно
   один раз — дубликат позволяет подсунуть значение мимо подписи;
2. `hash` сохраняется отдельно и исключается из подписываемых данных;
3. значения URL-декодируются, пары сортируются `a → z` и склеиваются
   через `\n`;
4. `secret_key = HMAC-SHA256(key="WebAppData", msg=BOT_TOKEN)`;
5. `hash = hex(HMAC-SHA256(key=secret_key, msg=launch_params))`;
6. сравнение с присланным значением — в постоянном времени.

Дополнительно отклоняются просроченные данные по `auth_date`: без этого
перехваченная строка запуска работала бы бессрочно.

`initDataUnsafe` для проверки не используется — он подделывается.
Идентификатор пользователя берётся только из проверенных данных и
никогда из тела запроса.

## Запуск

### Что нужно заранее

* **Docker Desktop** — запускает всё остальное.
* **Git** — требование к сдаче: нужен репозиторий с commit hash.
* **Токен бота** — выдают организаторы хакатона.
* **Сертификаты Минцифры** в `certs/` — см. [certs/README.md](certs/README.md).
  Без них запросы к API MAX падают с ошибкой TLS.

### Одна команда

```bash
docker compose up --build
```

Поднимаются Postgres и бэкенд. Перед первым запуском скопируйте
`.env.example` в `.env` и заполните `BOT_TOKEN`.

```bash
cp .env.example .env
```

В PowerShell:

```powershell
Copy-Item .env.example .env
```

### Остановка и повторный запуск

```bash
docker compose down
```

Данные Postgres лежат в именованном томе и переживают остановку —
следующий `docker compose up` поднимет то же состояние.

Удалить данные вместе с контейнерами:

```bash
docker compose down -v
```

Перезапустить один сервис, не трогая базу:

```bash
docker compose restart backend
```

Пересобрать после изменения зависимостей:

```bash
docker compose up --build backend
```

## Переменные окружения

Полный список с комментариями — в [.env.example](.env.example).
Обязательные для рабочего запуска отмечены звёздочкой.

| Переменная          | По умолчанию                   | Назначение                                       |
|---------------------|--------------------------------|--------------------------------------------------|
| `BOT_TOKEN` *       | —                              | токен чат-бота, даёт полный доступ к управлению   |
| `BOT_USERNAME`      | —                              | ник бота для диплинка `https://max.ru/<botName>`  |
| `MAX_API_BASE_URL`  | `https://platform-api2.max.ru` | домен API                                         |
| `MAX_API_TIMEOUT`   | `15`                           | таймаут запросов к MAX, секунды                   |
| `PUBLIC_BASE_URL` * | —                              | публичный HTTPS-адрес бэкенда (адрес туннеля)     |
| `WEBHOOK_PATH`      | `/webhook`                     | путь endpoint'а вебхука                           |
| `WEBHOOK_SECRET` *  | —                              | значение заголовка `X-Max-Bot-Api-Secret`         |
| `LAUNCH_DATA_TTL`   | `86400`                        | предельный возраст `auth_date`, секунды           |
| `CORS_ORIGINS`      | `*`                            | origin фронтенда через запятую                    |
| `DATABASE_URL`      | задаётся в compose             | строка подключения к Postgres                     |
| `EXTRA_CA_CERTS_DIR`| `/app/certs`                   | каталог с сертификатами Минцифры                  |
| `APP_ENV`           | `development`                  | в `production` скрывается `/docs`                 |
| `LOG_LEVEL`         | `INFO`                         | уровень логирования                               |

Секретов в репозитории нет: `.env` и `certs/*` перечислены в `.gitignore`.
Если токен хоть раз попал в историю коммитов, считайте его
скомпрометированным и перевыпустите.

## Внешние сервисы и интеграции

Их нельзя воспроизвести внутри Docker — для проверки решения нужны
условия ниже.

| Сервис               | Назначение                                | Что нужно для проверки                           |
|----------------------|-------------------------------------------|--------------------------------------------------|
| Платформа MAX        | доставка событий бота, отправка сообщений | действующий `BOT_TOKEN`                          |
| Сертификаты Минцифры | TLS-соединение с `platform-api2.max.ru`   | файлы в `certs/`, скачиваются с Госуслуг         |
| HTTPS-туннель        | публичный адрес вебхука на 443            | ngrok или аналог; адрес — в `PUBLIC_BASE_URL`    |
| CDN MAX              | библиотека MAX Bridge для фронтенда       | доступ в интернет из браузера                    |

Туннель нужен потому, что MAX доставляет события только на публичный
HTTPS-адрес с сертификатом доверенного центра. Бесплатный тариф ngrok
выдаёт новый домен при каждом перезапуске — после смены адреса подписку
нужно оформить заново.

## Работа с данными

Хранятся только те данные, что приходят из проверенных данных запуска и
событий бота:

* `users` — идентификатор в MAX, имя, ник, язык, ссылка на фото, метка
  запуска из диплинка, время первого и последнего визита;
* `bot_dialogs` — может ли бот писать пользователю (запустил он бота или
  остановил).

Идентификатор пользователя записывается только после проверки подписи.
Таблицы создаются автоматически при старте приложения.

Персональные данные из внешних систем на этом этапе не обрабатываются.

## Пошаговый сценарий проверки

**1. Подготовка**

```bash
cp .env.example .env
```

Заполните `BOT_TOKEN`, положите сертификаты в `certs/`.

**2. Запуск**

```bash
docker compose up --build
```

**3. Живость сервиса**

```bash
curl http://localhost:8000/health
```

Ожидается:

```json
{"status":"ok","env":"development","bot_configured":true,"webhook_secret_set":true}
```

**4. Связь с API MAX**

```bash
docker compose run --rm backend python -m scripts.check_connection
```

Скрипт печатает подхваченные сертификаты и ответ `GET /me`. Здесь же
видно ник бота — его стоит прописать в `BOT_USERNAME`.

**5. Тесты**

```bash
docker compose --profile test run --rm tests
```

Проверяются валидные данные запуска, подделанный идентификатор, чужой
токен, просроченный `auth_date`, дубликат параметра, а также соответствие
разбора официальному примеру из документации и соблюдение лимита отправки.

**6. API мини-приложения без самого MAX**

Генератор подписывает строку запуска вашим токеном, поэтому сервер
принимает её как настоящую:

```bash
docker compose run --rm backend python -m scripts.make_launch_data --curl
```

Выполните напечатанную команду — `GET /api/me` вернёт профиль.

**7. Вебхук**

Поднимите туннель на порт 8000, впишите его адрес в `PUBLIC_BASE_URL`,
затем:

```bash
docker compose run --rm backend python -m scripts.setup_webhook
```

Напишите боту в MAX — в логах `docker compose logs -f backend` появится
событие, а бот ответит в чат.

## Примеры ожидаемого поведения

| Действие                                     | Ответ                                                        |
|----------------------------------------------|--------------------------------------------------------------|
| `GET /api/me` с корректной строкой запуска   | `200` и профиль пользователя                                  |
| `GET /api/me` без заголовка `Authorization`  | `401`, «Нет заголовка Authorization с данными запуска»        |
| `GET /api/me` с изменённым `user.id`         | `401`, `{"code": "bad_signature"}`                            |
| `GET /api/me` со строкой старше `LAUNCH_DATA_TTL` | `401`, `{"code": "expired"}` — можно переоткрыть приложение |
| `POST /webhook` с неверным секретом          | `403`, событие не обрабатывается                              |
| `POST /webhook` с корректным секретом        | `200` сразу, обработка — после ответа                         |
| Пользователь запустил бота                   | бот присылает приветствие с кнопкой открытия приложения       |
| Отправка нескольких сообщений одному адресату| очередь выдерживает паузу ≥ 0,5 с между отправками            |

Проверить сценарии с ошибками:

```bash
# просроченные данные запуска
docker compose run --rm backend python -m scripts.make_launch_data --age 999999 --curl

# запрос без авторизации
curl -i http://localhost:8000/api/me
```

## Известные ограничения

* **Схема БД создаётся через `create_all`.** Новые таблицы появляются
  сами, но изменения в существующих не применяются. Для продакшена сюда
  нужен Alembic.
* **Сессии не заводятся.** Подпись проверяется на каждом запросе, срок
  жизни строки запуска ограничен `LAUNCH_DATA_TTL` (по умолчанию сутки).
  После истечения фронтенд должен переоткрыть мини-приложение.
* **Очередь отправки живёт в памяти процесса.** При нескольких репликах
  бэкенда лимит 2 сообщения в секунду перестанет соблюдаться — понадобится
  общий счётчик, например в Redis.
* **Повторная доставка событий не отслеживается.** При неудачном ответе
  MAX повторяет доставку до 10 раз, и одно событие может обработаться
  дважды. Обработчики, меняющие состояние, стоит делать идемпотентными.
* **Туннель в Docker не воспроизводится** и запускается отдельно.
* **`CORS_ORIGINS=*` годится только для разработки.** Перед сдачей
  подставьте адрес фронтенда.
* **Long Polling не поддерживается** сознательно: для продакшена
  документация требует вебхук, а при активной подписке Long Polling всё
  равно не работает.

## Грабли платформы

Собраны здесь, чтобы не наступать повторно:

* домен только `platform-api2.max.ru`, старый `platform-api.max.ru` не
  обслуживает ботов;
* токен только в заголовке `Authorization`, без `Bearer`, не в query;
* без сертификата Минцифры в доверенных — ошибка TLS на любом запросе;
* вебхук только по HTTPS на 443, самоподписанные сертификаты не
  принимаются;
* ответ на вебхук — 200 в течение 30 секунд, иначе событие считается
  недоставленным; после 8 часов неудач бот отписывается автоматически;
* `GET /chats` удалён, список чатов — через `POST /subscriptions`;
* в payload диплинка допустимы только `A-Z a-z 0-9 _ -`; пробелы и
  кириллица приводят к тому, что параметр молча вырезается;
* документация меняется часто — перед релизом стоит открывать
  [changelog API](https://dev.max.ru/docs-api/changelog-api) и
  [changelog платформы](https://dev.max.ru/docs/changelog-platform).
