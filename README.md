### Два контура аутентификации

Их легко перепутать, а это разные механизмы:

| Контур           | Кто обращается | Как подтверждает себя                       |
|------------------|----------------|---------------------------------------------|
| `POST /webhook`  | платформа MAX  | заголовок `X-Max-Bot-Api-Secret`            |
| `GET /api/*`     | мини-приложение| подпись данных запуска в `Authorization`    |

### Почему бот и API — один сервис

Вебхук обязан быть доступен по HTTPS на порту 443 с сертификатом
доверенного центра. Разносить бота и API по разным контейнерам значит
заводить два публичных адреса и два сертификата ради одного процесса.
Один домен — один сертификат. Модули `bot/` и `api/` разделены в коде,
так что при необходимости их можно развести по сервисам, не переписывая
логику.

С того же домена отдаётся и само мини-приложение, так что фронтенд и API
живут на одном origin: браузер не делает preflight и CORS в бою не
участвует. Публичный адрес — `https://my-olymp.ru`, границу на 443 держит
nginx из [`deploy/nginx/`](deploy/nginx/), а не приложение.

### Проверка данных запуска

Главная задача бэкенда. Мини-приложение получает от MAX подписанную
строку и присылает её на сервер; проверить подпись может только сервер,
потому что она считается на основе токена бота.

Алгоритм — [dev.max.ru/docs/webapps/validation](https://dev.max.ru/docs/webapps/validation),
реализация в [`launch_data.py`](backend/app/security/launch_data.py):

1. параметры разбираются на пары, каждый ключ обязан встречаться ровно
   один раз — дубликат позволяет подсунуть значение мимо подписи;
2. `hash` сохраняется отдельно и исключается из подписываемых данных;
3. значения URL-декодируются, пары сортируются `a → z` и склеиваются
   через `\n`;
4. `secret_key = HMAC-SHA256(key="WebAppData", msg=BOT_TOKEN)`;
5. `hash = hex(HMAC-SHA256(key=secret_key, msg=launch_params))`;
6. сравнение с присланным значением — в постоянном времени.

Дополнительно отклоняются просроченные данные по `auth_date`: без этого
перехваченная строка запуска работала бы бессрочно.

`initDataUnsafe` для проверки не используется — он подделывается.
Идентификатор пользователя берётся только из проверенных данных и
никогда из тела запроса.

### Одна запись каталога — олимпиада по предмету

Уровень по перечню РСОШ зависит от предмета: Московская олимпиада по
астрономии — I уровня, по биологии — II. Из 38 олимпиад, идущих сразу по
нескольким предметам, уровень различается у 27.

Поэтому запись в каталоге — это пара «олимпиада + предмет», а не
олимпиада целиком. Иначе уровень на карточке пришлось бы выбирать
наугад, а механика показывает его в каждом списке.

Описание, ссылка на сайт, классы и организаторы у всех предметов одной
олимпиады совпадают и просто дублируются.

Следствие: «Олимпиада СПбГУ» присутствует четырнадцать раз, и в «Мои
олимпиады» она добавляется тоже по предмету.

### Миграции схемы

Схему создаёт и обновляет Alembic — сервис применяет миграции сам при
старте, до запуска HTTP-сервера. Так одна и та же команда поднимает и
чистую базу, и уже существующую.

После изменения моделей:

```bash
docker compose run --rm backend alembic revision --autogenerate -m "что меняем"
```

Файл появится в `backend/migrations/versions/`; его нужно просмотреть
глазами и закоммитить. Применится он при следующем запуске.

### Точность дат — главная особенность каталога

Источник отдаёт даты этапов строками разной точности. В текущей выгрузке
из 97 этапов у **65 известен точный день**, у **32 — только месяц и год**
(«мар 2027»), а у 19 нет даты окончания.

Механика приложения считает «до этапа N дней», строит календарь по дням и
присылает утром сводку о событиях дня. Для этапа, о котором известен лишь
месяц, любой такой расчёт даст правдоподобное, но выдуманное число.

Поэтому дата хранится вместе с признаком точности, а API отдаёт это явно:

| Поле | Смысл |
|---|---|
| `start_precision` | `day` — известен день, `month` — только месяц |
| `days_until_start` | число дней или **`null`**, если точного дня нет |
| `plannable` | `false` — этап нельзя поставить в календарь по дням |
| `raw_date_range` | исходная строка источника: «мар 2027» |

**Договорённость с фронтендом:** если `days_until_start` равен `null`,
таймер показывать нельзя — вместо него выводится `raw_date_range` как есть.

Тип этапа (`kind`) определяется по названию и является предположением, а не
данными первоисточника. Значение `other` означает «определить не удалось»
— на текущей выгрузке таких 10 из 97.

## Запуск

### Что нужно заранее

* **Docker Desktop** — запускает всё остальное.
* **Git** — требование к сдаче: нужен репозиторий с commit hash.
* **Токен бота** — выдают организаторы хакатона.
* **Сертификаты Минцифры** в `certs/` — см. [certs/README.md](certs/README.md).
  Без них запросы к API MAX падают с ошибкой TLS.

### Одна команда

```bash
docker compose up --build
```

Поднимаются Postgres и бэкенд. Перед первым запуском скопируйте
`.env.example` в `.env` и заполните `BOT_TOKEN`.

```bash
cp .env.example .env
```

В PowerShell:

```powershell
Copy-Item .env.example .env
```

### Остановка и повторный запуск

```bash
docker compose down
```

Данные Postgres лежат в именованном томе и переживают остановку —
следующий `docker compose up` поднимет то же состояние.

Удалить данные вместе с контейнерами:

```bash
docker compose down -v
```

Перезапустить один сервис, не трогая базу:

```bash
docker compose restart backend
```

Пересобрать после изменения зависимостей:

```bash
docker compose up --build backend
```

### Запуск на сервере my-olymp.ru

Локальный `docker-compose.yml` поднимает только Postgres и бэкенд: наружу
он не смотрит и TLS не делает. Для сервера есть отдельный файл — он
добавляет nginx с сертификатом, отдаёт статику мини-приложения и убирает
порты бэкенда и базы с хоста:

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Первый выпуск сертификата, перерегистрация вебхука и привязка адреса к
боту — [docs/deploy-my-olymp.md](docs/deploy-my-olymp.md).

Публичный адрес нужен потому, что MAX доставляет события только на
HTTPS-адрес с сертификатом доверенного центра; самоподписанные не
принимаются.

Раньше эту роль играл туннель ngrok, и его адрес приходилось помнить и
перерегистрировать. Теперь адрес постоянный, и туннель нужен только для
отладки: тогда его адрес подставляется в `PUBLIC_BASE_URL`, а подписка
оформляется заново.

Как поднять сервер с нуля — [docs/deploy-my-olymp.md](docs/deploy-my-olymp.md).

## Работа с данными

Хранятся только те данные, что приходят из проверенных данных запуска и
событий бота:

* `users` — идентификатор в MAX, имя, ник, язык, ссылка на фото, метка
  запуска из диплинка, время первого и последнего визита;
* `bot_dialogs` — может ли бот писать пользователю (запустил он бота или
  остановил).

Каталог олимпиад:

* `olympiads` — название, ссылка на источник, вузы-партнёры, отметка о том,
  когда запись последний раз подтверждалась в источнике;
* `stages` — этапы с датами, точностью дат и предполагаемым типом;
* `subjects`, `categories` — справочники предметов и категорий.

Данные пользователя:

* `saved_olympiads` — что добавлено кнопкой «Буду писать»;
* `stage_progress` — ответы «прошёл / не прошёл» по этапам;
* `stage_plans` — какой этап на какой день запланирован в календаре;
* `user_settings` — класс, уведомления, режим для дальтоников.

Хранятся на сервере, а не в браузере: напоминания отправляет бот, и он
должен знать, за чем следит пользователь, даже когда мини-приложение
закрыто. Вкладка «Новости» отдельно не хранится — она вычисляется из дат
этапов и ответов пользователя.

Идентификатор пользователя записывается только после проверки подписи.
Таблицы создаются автоматически при старте приложения.

Персональные данные из внешних систем не обрабатываются.

### Источники данных

| Источник | Что даёт | Чего нет |
|---|---|---|
| `data/subjects.sample.json` | 166 записей: предметы, уровни, классы, описания, организаторы | этапов и дат |
| `data/olympiads_schedule.json` | 147 этапов с датами у 61 олимпиады | всего остального |
| `data/olympiads.sample.json` | 97 этапов у 20 олимпиад, другой источник | предмета и уровня |

Первый файл наполняет каталог, второй доставляет в него даты. До
появления второго «Поиск» работал на каталоге, а «Календарь» и «Новости»
— на третьем файле, чьи записи предмету не принадлежат и потому в
интерфейсе не видны. Теперь даты приходят прямо в каталожные олимпиады,
и обе вкладки работают на тех же записях, что и поиск.

Расписание снимается с olimpiada.ru отдельным парсером
([`tools/olympiad_schedule_parser.py`](tools/olympiad_schedule_parser.py)) и
кладётся в базу командой `python -m scripts.import_schedule`. Связать его
с каталогом напрямую нечем: парсер знает олимпиады по `activity_id`
olimpiada.ru, а база — по `id` из каталога. Соответствие берётся из
`data/subjects.olimpiada.json` — это тот же каталог, размеченный
идентификаторами olimpiada.ru. Импортируется он не как каталог, а только
как таблица соответствия.

Расписание есть не у всех: на olimpiada.ru его нет у 85 олимпиад из 146.
Записи разных источников различаются полем `source` и друг другу не
мешают.

#### Форма сроков этапа

Парсер размечает сроки четырьмя способами, и каждый рисуется в календаре
по-своему. В базе для этого нет отдельного поля: всё выражено тем, какие
из дат заполнены, а обратно значение вычисляет `presentation.date_precision`
и отдаёт в API полем `date_precision`.

| Значение | `starts_on` | `ends_on` | Как показывать |
|---|---|---|---|
| `range` | начало | конец | непрерывная полоса цвета предмета |
| `exact` | день | — | кружок в цвет олимпиады |
| `until` | — | дедлайн | полоса, набирающая непрозрачность к последнему дню |
| `unknown` | — | — | в календаре не показывать |

Вычисление, а не хранение, выбрано намеренно: значение не может разойтись
с датами, по которым посчитано. Дата с точностью до месяца попадает в
`unknown` — конкретного дня у неё нет, а календарь размечает дни; сама
точность при этом остаётся в `start_precision` и `raw_date_range`.

```bash
docker compose run --rm backend python -m scripts.import_schedule
```

Последний шаг не пропускайте: без него у олимпиад каталога нет дат, и
«Календарь» с «Новостями» пусты.

Импорт идемпотентен: повторный запуск обновляет записи на месте, а не
дублирует их. Обновление на месте принципиально — прогресс пользователя
по этапам ссылается на строки таблицы `stages`, и пересоздание обнуляло бы
его при каждом обновлении данных.

Данные собраны парсером с `postupi.online` и являются срезом на момент
выгрузки. Дата последней проверки записи отдаётся в поле
`source_checked_at`.

## Утренние напоминания

Раз в день, в `REMINDER_TIME`, бот присылает сводку по олимпиадам, за
которыми пользователь следит. Одну, а не по сообщению на событие: в сезон
у школьника с пятью олимпиадами набегает по нескольку событий в день, и
десяток уведомлений он просто выключит.

Что попадает в сводку — у одного этапа не больше одной строки:

| Блок | Что в нём |
|---|---|
| Сегодня | запланированный на сегодня этап, начало этапа, последний день |
| Завтра | то же про завтра |
| Через 3 дня | последний день этапа — чтобы успеть доделать работу |
| Как прошло? | этап закончился вчера, а ответа «прошёл / не прошёл» нет |

Только события с точным днём: «начинается завтра» про этап «март 2027»
было бы выдумкой. Сказать нечего — сообщения нет вовсе: пустая сводка
приучает не открывать сообщения бота.

Кому: тем, кто запустил бота (иначе MAX писать не разрешит), не выключил
уведомления в мини-приложении и следит хотя бы за одной олимпиадой.

Время у этапов в источнике не указано — только даты. Поэтому
напоминание «за час до начала» невозможно, и роль его играет сводка
утром в день события и накануне.

**Как не написать дважды.** Перед отправкой в таблицу `reminder_log`
вставляется строка «пользователь + день»; первичный ключ делает вставку
замком. Бэкенд можно перезапускать сколько угодно: поднявшись в 9:40
после сбоя, он разошлёт тем, кому не успел, и не тронет остальных. Если
MAX недоступен, проход прерывается и повторяется через 10 минут; ошибка
по одному человеку — например, удалённый диалог — остальных не задевает.
Позже 21:00 рассылка не начинается: «что важно сегодня» ночью — уже не
напоминание.

**Проверить на себе, не дожидаясь утра:**

```bash
python -m scripts.send_reminders --users                     # найти свой id
python -m scripts.send_reminders --dry-run                   # что уйдёт сегодня, без отправки
python -m scripts.send_reminders --dry-run --date 2026-10-14 # как будто сегодня 14 октября
python -m scripts.send_reminders --user <id> --date 2026-10-14 --force
```

Если сводка кому-то не придёт, `--user <id>` скажет почему: от человека
не было событий бота, уведомления выключены или сохранённых олимпиад нет.
С `--dry-run` он и в этом случае покажет текст сводки. Что именно бот
прислал, лежит в `reminder_log.text`.

О том, что человек запустил бота, сервер узнаёт только из событий MAX, а
их нет без подписки на вебхук. Бэкенд проверяет подписку при старте и
пишет в лог строку: «Подписка на события MAX: …» — всё в порядке, «MAX не
присылает события на …» — нужен `python -m scripts.setup_webhook`. Кто
запустил бота, пока подписки не было, отмечается первым же своим
сообщением боту: `bot_started` приходит лишь однажды.

## Известные ограничения

* **Сессии не заводятся.** Подпись проверяется на каждом запросе, срок
  жизни строки запуска ограничен `LAUNCH_DATA_TTL` (по умолчанию сутки).
  После истечения фронтенд должен переоткрыть мини-приложение.
* **Рассылка живёт в процессе бэкенда.** Отдельной службы нет, поэтому
  если бэкенд лежит с утра до 21:00, сводка в этот день не уйдёт. Двойной
  отправки при нескольких процессах не будет — замок в базе, — но
  рассылать будет только один из них.
* **Очередь отправки живёт в памяти процесса.** При нескольких репликах
  бэкенда лимит 2 сообщения в секунду перестанет соблюдаться — понадобится
  общий счётчик, например в Redis.
* **Повторная доставка событий не отслеживается.** При неудачном ответе
  MAX повторяет доставку до 10 раз, и одно событие может обработаться
  дважды. Обработчики, меняющие состояние, стоит делать идемпотентными.
* **Данные собраны из двух источников.** У записей с предметами нет
  этапов, у записей с этапами нет предмета — см. «Два источника данных».
* **Категорий и подкатегорий пока нет.** Механика предполагает уровень
  «категория → подкатегория → предмет»; в данных есть только предметы,
  таблица категорий пустая.
* **Тип этапа — эвристика по названию**, а не данные источника.
* **Треть этапов не имеет точного дня начала** — для них недоступны
  таймеры, календарь по дням и утренние напоминания.
* **Источник бывает недоступен.** Приложение работает на сохранённых
  данных; дата последней проверки видна в `source_checked_at`.
* **Отмена ответа «не прошёл» не восстанавливает планы.** При этом
  ответе планы и ответы по следующим этапам удаляются; после отмены их
  нужно поставить заново.
* **Правила механики — в одной точке.** Лимит «три в день» и блокировки
  проверяются на сервере; интерфейс может их не дублировать, но должен
  показывать ответ сервера.
* **Публичный адрес нужен даже для отладки вебхука.** MAX не доставляет
  события на `localhost`: либо сервер на `my-olymp.ru`, либо туннель.
* **`CORS_ORIGINS` — список, а не `*`.** В бою фронтенд и API на одном
  origin, и CORS не участвует; звёздочка понадобилась бы только для
  копии страницы на стороннем адресе.
* **Long Polling не поддерживается** сознательно: для продакшена
  документация требует вебхук, а при активной подписке Long Polling всё
  равно не работает.

## Грабли платформы

Собраны здесь, чтобы не наступать повторно:

* домен только `platform-api2.max.ru`, старый `platform-api.max.ru` не
  обслуживает ботов;
* токен только в заголовке `Authorization`, без `Bearer`, не в query;
* без сертификата Минцифры в доверенных — ошибка TLS на любом запросе;
* вебхук только по HTTPS на 443, самоподписанные сертификаты не
  принимаются;
* ответ на вебхук — 200 в течение 30 секунд, иначе событие считается
  недоставленным; после 8 часов неудач бот отписывается автоматически;
* `GET /chats` удалён, список чатов — через `POST /subscriptions`;
* в payload диплинка допустимы только `A-Z a-z 0-9 _ -`; пробелы и
  кириллица приводят к тому, что параметр молча вырезается;
* документация меняется часто — перед релизом стоит открывать
  [changelog API](https://dev.max.ru/docs-api/changelog-api) и
  [changelog платформы](https://dev.max.ru/docs/changelog-platform).
